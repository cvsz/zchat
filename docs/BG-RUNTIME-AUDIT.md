# Background Runtime and Silent Behavior Audit

## Scope

This audit covers the tracked Windows application entry points, worker launch paths, notification and sound APIs, the LINE Status Changer scheduler, and the ZChat Control Server agent. The source baseline is `b51b8d3821bb5524da1ea6a4f9135bdf72a1a151`. A local untracked `zchat-client/` directory was inventoried separately and was not modified or included in this change.

## Findings

Windows notification-area icon registration exists in several applications; registering an icon is distinct from sending a balloon notification.

## Implementation detail

`LineStatusChanger.report_callback_exception` now checks Tk's window state before opening a dialog. States `iconic` and `withdrawn` are treated as background execution. The exception is logged before this check, and the status label is updated so the failure is visible when the user restores the window. If Tk cannot report its state or show the dialog, a debug record is written and the callback handler does not raise another UI exception.

The change is scoped to the confirmed background-modal path. A shared `APP_*` configuration was not added because the audited applications have no active desktop notification caller to wire into such a setting; adding unused environment switches would not suppress an existing behavior. It does not mute Windows, alter system notification settings, or change selected WAV playback.

## Follow-up: bounded Camfrog status-control messages

The status adapter now uses `SendMessageTimeoutW` with `SMTO_ABORTIFHUNG` for cross-process reads and writes to Camfrog controls. A hung or non-responsive client therefore causes the individual control request to fail closed instead of blocking the worker indefinitely. Each message has a 1-second ceiling; this is not a bound on total end-to-end operation time, and mocked tests do not establish behavior against a live Camfrog window.

The shared status engine reports `CLIENT_STATE_CONFIRMED` when the requested text is observed in Camfrog's local status combo. This confirms only the client UI state; it does not establish that Camfrog's servers or other users observe the status. External status verification remains unavailable and must not be reported as `VERIFIED_APPLIED`.

The status execution evidence records `foreground_matches_before_submit` and `foreground_matches_before_and_after`. In strict Windows mode, the engine now refuses to post Enter if the foreground HWND changed or could not be sampled between the initial snapshot and the pre-submit check. It also returns `BACKGROUND_UNSUPPORTED` after submit if endpoint samples differ or are unavailable. These checks cannot prove that focus did not change briefly between samples or as a consequence of the submit message itself. A live source-engine smoke test against Camfrog 8.5.0.51219 showed the temporary status in the client and restored the prior client status; the cursor and clipboard sequence stayed unchanged, but the foreground HWND differed between endpoints. A separate live read-only attach preserved foreground across discovery. The submit path remains unverified for strict background isolation; external provider state and packaged executable behavior also remain unverified.

On 2026-10-18, a native Windows read-only probe against the running Camfrog 8.5.0.51219 process verified the signed process, classified its main directory window, confirmed the status control HWNDs still belonged to that process, and observed the same foreground HWND before and after discovery. No status text was written or submitted. The Windows Python 3.12.10 suite `tests/test_status_gui.py`, `tests/test_camfrog_status_engine.py`, `tests/test_camfrog_emergency_stop.py`, and `tests/test_camfrog_profile_status.py` passed (107 tests). This proves current process/control discovery and mocked behavior on Windows; it does not test the submit path, transient focus changes, provider visibility, or the packaged EXE.

The current Windows 11 x64 PyInstaller 6.22.3 candidate is at `dist/status-changer-candidate/status-changer-candidate.exe`. SHA-256: `57214a971e914828bcdd235f922bedbb9fb8fc86f4d02194cec0e5188b3942d2`. Its `--worker --help` smoke test exited successfully after copying the EXE to a temporary directory outside the repository. The local `BUILD-MANIFEST.txt` records matching executable and source hashes. The candidate is unsigned and has startup/package evidence only; it does not perform a live status change because strict submission remains `BACKGROUND_UNSUPPORTED`. PyInstaller warned that this build was run elevated; rebuild from a non-administrator terminal before any release use.

On 2026-10-18, the shared executor gained a fail-closed capability gate before it writes text into Camfrog. The current 8.5 adapter explicitly reports that its Enter-message submit path is not proven to preserve foreground state; strict execution returns `BACKGROUND_UNSUPPORTED` with `STRICT_SUBMIT_UNVERIFIED` and performs no status write. The legacy submit sequence remains available only to callers that explicitly select a non-strict mode. The profile HTTPS flow remains in Web Status and is not silently used as a Status Changer fallback. A live strict preflight returned the expected refusal before staging text; foreground, cursor, and clipboard sequence were unchanged. The keyboard-state snapshot changed during the probe, so keyboard-state isolation remains inconclusive. The updated candidate is documented above.

A follow-up native Windows 10.0.26300.0 / Python 3.14.8 preflight against the running, signed Camfrog 8.5.0.51219 process returned `BACKGROUND_UNSUPPORTED / STRICT_SUBMIT_UNVERIFIED` from `verification_source=submit_capability`; the executor's gate runs before `write_text_no_focus` or submit. Foreground HWND, keyboard-state digest, and clipboard sequence matched at the endpoints. Cursor coordinates differed, and the observation cannot attribute that movement to this process or another desktop actor. The sanitized record is stored at `%LOCALAPPDATA%\ZChat\status-changer\strict-preflight.jsonl`; it contains no requested status text. Provider state was not verified. The live submit probe now uses the same `pid_<pid>` Windows mutex as the shared executor and checks the `camfrog.status-changer` emergency-stop scope before staging and again before sending; its messages remain exploratory and do not establish strict capability.

`tools/probe_submit_routes.py` is an opt-in live experiment: it can leave its test status applied in Camfrog and cannot prove that focus was never transiently changed. It restores the previous local edit draft when the target remains valid, including staging and route exceptions, and writes sanitized outcome/error metadata to `%LOCALAPPDATA%\\ZChat\\status-changer\\submit-probe.jsonl`. A route exception is recorded as `EFFECT_UNKNOWN`; no automatic retry or provider-status rollback is attempted. Do not use it as evidence of strict-background support without observing the desktop and independently verifying the provider-visible status.

The Windows `CBN_SELENDOK` notification is documented as the notification sent when a user selects a combo-box list item, and `CBN_SELCHANGE` is sent when the current selection changes ([Microsoft Learn: CBN_SELENDOK](https://learn.microsoft.com/en-us/windows/win32/controls/cbn-selendok), [About Combo Boxes](https://learn.microsoft.com/en-us/windows/win32/controls/about-combo-boxes)). This is not evidence that synthesizing those notifications will make Camfrog commit a typed status. No alternative no-focus submit protocol has been verified, so the strict capability gate remains closed.

On 2026-10-18, a fresh read-only attachment verified one signed Camfrog 8.5.0.51219 process and enumerated 96 top-level windows, of which 7 were visible. The visible classified windows were one main directory and one IM window; no room window was classified, and no window title matched the configured test room. A sanitized scan of the main directory found configured account-name matches only on hidden `CTreeViewTS` tree items, which may be contact entries and do not identify the signed-in account. The main directory establishes only local client UI state, not a canonical provider-account identity. No write was attempted. Consequently, this runtime cannot provide the requested room or recipient Friends List acceptance evidence.

The cross-process status mutex now declares pointer-sized `HANDLE` and explicit Win32 function signatures. Before this fix, ctypes' default C `int` return type could truncate a mutex handle on 64-bit Windows. A native Windows regression test now spawns a separate process, verifies that the parent cannot acquire the same named mutex while the child holds it, and confirms clean release. This proves local Windows logon-session process coordination only; it does not prove account identity or coordination across machines.

Random Status, Marquee Status, and the combined Status Changer now acquire one shared local writer mutex for the full worker lifetime. This prevents those local workers from alternating writes to the same Camfrog status control. The mutex is scoped to a Windows logon session and does not coordinate separate machines or prove which provider account is signed in. If the mutex cannot be acquired, the worker exits before creating its PID file or starting `Runner`.

All three status applications now check strict-background submit capability before starting a live worker through either the GUI launcher, CLI `start`, or the worker `run` entry point. An unsupported provider path exits with `BACKGROUND_UNSUPPORTED` before spawning a process or entering the retry loop. Marquee's strict-mode recovery also preserves that result instead of falling through to legacy UI Automation discovery, which previously added a misleading process-selection error after the write had already been refused. Dry-run workers remain non-mutating.

A later Windows 11 x64 build on Python 3.12.10 / PyInstaller 6.22.3 produced separate candidate executables at `dist/status-marquee-candidate/status-marquee.exe`, `dist/status-random-candidate/status-random.exe`, and `dist/status-changer-candidate/status-changer.exe`. Their SHA-256 values are `e66fa547f2a11f2660344e4e8d9e5c3ce326756276899d53453c395fd38bcf96`, `427f6388b43c7e007501b954f29f6762284840e32eb1e0e8bbb25897264ba746`, and `03503f9076e7c0305ea4fb2e44dc7314156286e175e4e99279e9765c7e57a0f5`, respectively. All three packaged `--worker --help` smoke checks succeeded. Isolated live-start checks returned exit code 2 before leaving a worker process. These candidate builds were produced from a dirty worktree in an elevated terminal and are unsigned; they are local test artifacts, not release artifacts. No external Camfrog status was changed or verified.

The local emergency-stop registry stores active stops and their audit history in a per-user SQLite database so separate ZChat processes on the same machine observe the same stop. The status executor checks that stop before staging text and again immediately before submitting it. A stop racing after the final check cannot cancel a submitted Win32 message. This is local process coordination only; it does not provide multi-machine authority, tamper-proof audit storage, or an inventory of all in-flight operations.

Status feature callers now check `FEATURE` scope using stable local resource keys (`camfrog.status`, `camfrog.status-changer`, `camfrog.status-random`, and `camfrog.status-marquee`). A local operator can activate or inspect stops with `python src/camfrog/camfrog_emergency_stop.py activate --scope FEATURE --reason OPERATOR_HALT --operator LOCAL_OPERATOR --resource camfrog.status-random`, `... status`, and `... deactivate --scope FEATURE --resource camfrog.status-random`. The CLI attribution field is not an authenticated operator identity; host access controls remain the local authorization boundary. This does not revoke server-side commands or establish account identity across machines.

## Evidence and remaining gates

- `line/tests/test_core.py`: 51 unit tests passed on Linux/WSL and 51 passed on native Windows. Callback-error tests mock Tk state and dialogs; tray retry tests assert captured warning records.
- `make ci` on the candidate code: repository validation passed; formatting and lint passed; root tests reported 710 passed and 3 skipped; control-server tests reported 40 passed; both dependency audits reported no known vulnerabilities (the editable control-server distribution is excluded from the installed-package audit).
- Static inspection found no active caller of `LineTrayIcon.notify`.
- `line/build.bat` completed successfully in a native Windows worktree and produced `line-status-changer.exe`.
- `line/tools/smoke_line_x.py` passed against the packaged executable: title-bar X hid the window to the tray, and tray Exit closed the process cleanly.
- The Windows smoke did not inject a callback failure or capture audio; audible-output acceptance remains unverified.
- The control server explicitly documents that its Windows process/URI behavior lacks Windows runtime acceptance and that the service is not production-ready. See [control-server/README.md](../control-server/README.md).
- The requested client reconstruction remains blocked by the absence of client source and a chat-server contract. See [the reconstruction status](../zchat-client-re/IMPLEMENTATION_STATUS.md).

No production-readiness or deployment claim is made by this audit.
